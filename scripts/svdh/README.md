# svdh — the evaluation harness for ganita's SVD

svdh scores `ganita_mat_svd` (the full decomposition) and `_linalg_svd_impl(m, 0, s, 0, 0)` (the
values-only path behind `rank` and `condition`) from any ganita tree. It compares them against an
exact oracle on a fixed corpus of 20,622 matrices, and against two adversarial sets. It also runs
hunts that need no oracle. These are the measurements behind the numbers in `ganita_mat_svd`'s
comment (`src/linalg.cyr`), in [ADR 0005](../../docs/adr/0005-svd-is-jacobi-on-a-pivoted-qr.md)
and in the 1.2.12 entry of the [CHANGELOG](../../CHANGELOG.md). Re-run it after any change to the
SVD, and compare against the reference results below.

Everything is deterministic. With the versions and the BLAS kernels under
[Requirements](#requirements-and-setup), the generators rebuild every corpus byte for byte (the
reference checksums are below), and the drivers give bit-identical results files on x86_64 and on
aarch64 (qemu); `run.sh`, `adv/run.sh` and `hunts/run.sh` each have an aarch64 mode that checks
this, and exits 1 when it does not hold.
The one exception is the rank / condition / pseudo_inv file of `adv/driver_rcp.cyr`, which can
differ in the sign of a NaN entry of `pseudo_inv`, because the two architectures' default NaN
differs (on `adv`, 12,769 words in 192 matrices are `0xfff8…` on x86_64 and `0x7ff8…` on
aarch64). `adv/run.sh` accepts that difference and no other (`adv/rcpcmp.py`).

## Requirements and setup

- `cyrius` on `PATH`, at the version `cyrius.cyml` pins. The scripts use whatever `cyrius` and
  `CYRIUS_HOME` are in the environment and warn when `cyrius version` reports another version.
- Python 3 with `mpmath==1.4.1` and `numpy==2.5.0` (`requirements.txt`, which also records the
  Python the reference files were made with, 3.14.7). Other versions run, but every generator
  (and every shell script that runs Python) warns, since they may not regenerate the reference
  files byte for byte: numpy picks the well-conditioned factors of the `graded` class, and its
  result is recorded in the oracle's verification log.
- For the generators, numpy's own OpenBLAS (the one its wheels bundle) running its `Haswell`
  kernels with 16 threads, as when the reference files were made (`requirements.txt`). Some
  generated bytes go through numpy's BLAS and LAPACK: `corpus.py` picks the factors of `graded` by
  numpy's κ and records numpy's distance to the oracle in its verification log; `adv/gen.py` builds
  `bunder`, `brestart` and `atall2` with numpy's dot products and norms, and computes the `kappa`
  values and the σ of the two big `bigdef` matrices with numpy; the `boundary` family of
  `hunts/gen.py` (`s5`) scales by numpy's σ₁. Each CPU family has its own kernels, and OpenBLAS
  splits some calls between its threads, so the entries of `atall2` (16,384 to 262,144 rows) and
  the numpy σ of `bigdef` also depend on the thread count, measured ad hoc (the entries of `bunder`
  and `brestart`, of 4,096 rows at most, do not). The generators and `adv/hunt.py` set 16 threads
  themselves (also on fewer CPUs; `adv/gen.py` in its oracle processes too), and warn when OpenBLAS
  runs other kernels or cannot be found; on an x86_64 CPU with AVX2 and FMA,
  `OPENBLAS_CORETYPE=Haswell` in the environment selects those kernels. With other kernels (checked
  ad hoc with `OPENBLAS_CORETYPE=Sandybridge`), the corpus's `oracle.json` (its verification log
  only), the three files of `adv`, and `s5`'s corpus and oracle come out different, and so may the
  matrices of `adv/hunt.py`'s `tall2` and `eqn` families and its `nw` flags, which go through numpy
  too. On such a host (aarch64 included), copy the reference sets from an x86_64 one. The scorers
  and the drivers use no BLAS: the scorers' arithmetic is numpy's own longdouble code.
- Scoring needs a numpy `longdouble` with a 64-bit significand or wider: x87 80-bit on x86_64
  Linux, binary128 on aarch64 Linux. `check.py` and the other scorers refuse to run where it is
  plain double (macOS on arm64, Windows).
- bash 5.0 or later (the scripts time with `$EPOCHREALTIME`), git and tar; `qemu-aarch64` for
  the aarch64 runs.

From the repository root:

```sh
python3 -m venv build/svdh/venv
build/svdh/venv/bin/pip install -r scripts/svdh/requirements.txt
. build/svdh/venv/bin/activate
```

After the activation, `python3` is the venv's. The shell scripts run `$PY`, which defaults to
`python3`; set `PY` to use another interpreter.

Generated data never goes into `scripts/svdh` (Python's own `__pycache__` aside, which git
ignores). It goes to `$SVDH_WORK`, which defaults to `build/svdh` (git ignores `build/`):
corpora, oracles, results, summaries and driver binaries. Set `SVDH_WORK` to keep two
experiments apart. The commands below assume the default, and are run from the repository root.
The generators write a set's `corpus.bin`, `corpus_meta.json` and `oracle.json` under
temporary names and rename them together at the end, so a failed or interrupted run (Ctrl-C or
SIGTERM included) leaves the previous set as it was. When `corpus.py`'s self-checks fail, it
keeps the new files as `corpus.bin.failed`, `corpus_meta.json.failed` and `oracle.json.failed`
instead, beside the previous set, and `check.py` warns when it is given an oracle that failed
them.

The times quoted here are for an idle 16-CPU x86_64 machine. The generators run one oracle
process per CPU (`--procs N` to change it; no output byte depends on it), and their wall time
is bound by the slowest single matrix, so under load it grows well past these figures.

## Quick start

```sh
python3 scripts/svdh/corpus.py          # corpus + exact oracle -> build/svdh (about 20 s)
python3 scripts/svdh/oracle_xcheck.py   # optional: an independent check of the oracle (a few seconds)
scripts/svdh/run.sh . cur               # build the driver from this tree, run it, score it
scripts/svdh/run.sh . cur aarch64       # the same under qemu-aarch64, plus a bit-for-bit diff
scripts/svdh/bench.sh . cur             # timings
```

Every script that takes arguments answers `-h` and `--help` with its usage and exits 0. A Python
script exits with status 2, with a message, on a usage error and when an input is missing or
does not fit, and with status 1 for a negative answer: an entry that `oracle_xcheck.py` finds in
disagreement, two results files that `check.py --diff` finds different (it exits 0 when they are
bit-identical, as `cmp` does), a failed self-check of `corpus.py`, a driver that fails, and
`hitstat.py --select` finding no hit. The shell scripts exit 2 on a usage error or a missing
input, and 1 when a step fails.

Inputs that do not fit are a file that cannot be read, a binary file whose size is not a whole
number of 8-byte words, a results file whose length is not the one the corpus's shapes give, and
a corpus, meta file and oracle from different sets: each meta entry's `id`, `rows` and `cols` must
be the corpus matrix's (integers, with `class` and `label` strings), and the oracle must give each
matrix as many σ as columns, reject exactly the matrices with a NaN or infinite entry, have σ²
that sum to ‖A‖²_F (to 2^−24 relative), and, where it records class counts (`corpus.py` and
`adv/gen.py` write them), have the meta file's. A meta file reordered among matrices of the same
shape, or an oracle of other matrices with the same Frobenius norms (to 2^−24), still passes. A
results file is bound to its corpus only by its length: the results of another corpus with the
same shapes in the same order are scored (and show up as failures), not refused.

A label (`run.sh`, `bench.sh`, `adv/build.sh`, and every script that runs their drivers or reads
their output) becomes part of file names, so it may hold only letters, digits, `.`, `_`, `+` and
`-`, and may not start with `-`. The aarch64 modes append `_a64` to it, so a label given to `run.sh`
or `adv/build.sh` may not end in `_a64`. A script that takes several labels refuses one given twice.
The scripts that run a driver take the `_a64` label and run that driver under qemu-aarch64;
`adv/run.sh` and `hunts/run.sh` first check that it is an aarch64 binary.

`run.sh <tree> <label> [aarch64]` builds `driver.cyr` with `<tree>` as the working directory, so
the binary is built from that tree's `src/` and `lib/`. It writes:
- `build/svdh/build/driver_<label>`, the driver;
- `results_<label>.bin`, the results;
- `summary_<label>.txt` and `summary_<label>.json`, the score;
- `time_<label>.txt`, the driver's wall time.

It removes the label's old driver, results, time and summary first, so that none is left from an
earlier run: a failed build leaves none of them, a driver that fails only the driver, and a
scoring that fails the driver, results and time, without a summary. It exits non-zero, with a
message, when the build, the driver or the scoring fails, and when the driver reports a call that
modified A (or prints no count of them).
The aarch64 run appends `_a64` to the label and diffs its results bit for bit against
`results_<label>.bin`: it exits 1 when they differ, and says so when there is no
`results_<label>.bin` to compare against. Extra build flags go in `DRIVER_FLAGS`, for example
`DRIVER_FLAGS="-D SVDH_NO_RESET"`.

The current `src/` should end with `PASS total: 20622 / 20622`, and its results file should have
the reference checksum given under [Reference results](#reference-results-1212).

## Comparing trees

A tree is any directory that holds `src/` and `lib/`. The label `base` is special: when
`build/svdh/results_base.bin` exists, every other run is also compared against it.

**Against a baseline revision.** `tree-at.sh <git-rev> <dir>` exports `src/` at that revision
with `git archive` (the working tree is not touched) and links `lib` to the repository's `lib/`.
For 1.2.11 (the tag `1.2.11`; its `src/` is also the one at commit 1805459):

```sh
scripts/svdh/tree-at.sh 1.2.11 build/svdh/tree-1.2.11
scripts/svdh/run.sh build/svdh/tree-1.2.11 base
scripts/svdh/run.sh . cur               # now also reports "vs baseline" and REGRESSIONS
```

**A candidate against the current `src/`.** Copy the tree, change the copy, and compare the two
results files:

```sh
mkdir -p build/svdh/cand && cp -r src build/svdh/cand/ && ln -s "$PWD/lib" build/svdh/cand/lib
# ... edit build/svdh/cand/src/linalg.cyr ...
scripts/svdh/run.sh . cur
scripts/svdh/run.sh build/svdh/cand cand
python3 scripts/svdh/check.py build/svdh/results_cand.bin --baseline build/svdh/results_cur.bin --sub
python3 scripts/svdh/check.py build/svdh/results_cand.bin --diff build/svdh/results_cur.bin
python3 scripts/svdh/tools/cmpres.py build/svdh/results_cand.bin build/svdh/results_cur.bin
```

`--baseline` gives, per class:
- how many of the baseline's status-0 matrices keep bit-identical S, U and Vt (`all=` means all
  three);
- `b0c!0`: the baseline returned 0 and the candidate did not;
- `fixed` (the baseline failed, the candidate returns 0) and `newPASS`.

It then lists **REGRESSIONS**: a status 0 that became non-zero, a PASS that became a fail, or a
metric where the candidate exceeds 4 × the baseline + a slack (4 for `sig_nw` and `sig_rel`, 16
for the orthogonality metrics and `recon`). A regression is not a failure, so read the reason:
1.2.12 has 174 against 1.2.11, every one a growth of `sig_rel` on a matrix that passes (the
listing stops at 60; `--json` holds them all, with each one's reasons), and `sig_rel` is not
part of PASS (see [Metrics and PASS](#metrics-and-pass-checkpy)).

`--diff` only says which matrices differ bit for bit. `tools/cmpres.py` shows the metrics of each
matrix whose bits changed. Run the same pair through the adversarial sets and the hunts too
(below): they reach inputs the corpus does not.

## File formats

All binary files are little-endian u64 / i64 words.

- **corpus.bin**: `count`, then per matrix `rows`, `cols` and `rows·cols` f64 bit patterns, row
  major. Every matrix has rows ≥ cols ≥ 1.
- **corpus_meta.json**: `[{id, class, label, rows, cols}]`. The adversarial sets add `kappa` and
  `grading` on some matrices: the condition number of the row- or column-normalised matrix.
- **results.bin** (`driver.cyr`, `driver_adv.cyr`), per matrix, in corpus order: `status` (i64,
  `ganita_mat_svd`), `n` σ bits, `m·n` U bits (row major), `n·n` Vt bits, `status_vo` (i64,
  `_linalg_svd_impl(A, 0, S2, 0, 0)`), `n` σ bits. That is 8·(2 + 2n + mn + n²) bytes per
  matrix. Before each call every out-param word is set to the poison `0x7FF4000000000BAD`, so
  output that was not written stays visible.
- **times_\<L\>.bin** (`driver_adv.cyr`, fd 3): per matrix, two i64, the nanoseconds of the full
  call and of the values-only call, from `clock_gettime(CLOCK_MONOTONIC)` (syscall 228, which
  cyrius renumbers for an aarch64 build). An aarch64 driver under qemu records real times, but
  of the emulation (several times the x86_64 ones), not of aarch64 hardware.
- **rcp_\<L\>.bin** (`driver_rcp.cyr`), per matrix: the values-only status, S[0], `rank(A, 0)`,
  tol = 1e-12·σ₁ (0 when the status is not 0), `rank(A, tol)`, `condition(A)`, then 1 and the
  n×m `pseudo_inv(A)`, or 0 when it returned null. A NaN in `pseudo_inv` has the sign of the
  architecture's default NaN, so this file can differ between x86_64 and aarch64 there.
- **oracle.json**: `{"info": {...}, "matrices": [...]}`, per matrix:
  - `reject`, true only for the non-finite inputs, which have no SVD;
  - `sigma_bits`, the exact σ in descending order, each rounded once to double (hex);
  - `hp`, `[m, e]` with σ ≈ m·2^e and 2^63 ≤ m < 2^64: the exact σ to 64 bits, which the metrics
    use, finite even where σ > DBL_MAX;
  - `rel_ok`, whether that σ is certified (below);
  - `rank` (exact; numerical, from numpy's σ, for the method `numpy`), `method` (`n1`,
    `n2-closed`, `mp-svd`, `zero`; also `numpy`, `blocks`, `lams` and `gram` in the other sets)
    and `prec` (the bits used; 0 where the method records none: `zero`, an exact zero matrix, and
    `blocks`, whose σ come from each block's own oracle).
- **hunt hits** (`adv/hunt.py`, `adv/hunt_hits.json`, `adv/nw_sample.json`): a JSON list of
  `{label, rows, cols, tree, why, bits}`: a non-empty string `label`, integers `rows` ≥ `cols` ≥ 1,
  `bits` as 16-digit hex strings, row major, with no NaN or infinite entry, and, where present, a
  string `tree` and a list of strings `why`. `mkwit.py` reads the same list (only `label`,
  `rows`, `cols` and `bits`), and so does `adv/gen.py --hits` (also `why`); `tools/hitstat.py`
  counts them. Each of them, and `hunt.py` adding to a hit file, refuses with status 2 a file
  with another entry. Some hit labels and `tree` fields in `adv/hunt_hits.json` and
  `adv/b_m3_small.json` name the draft trees the hunt ran on; they are kept as recorded, since
  the `cycle` labels are part of `adv/corpus_meta.json`'s checksum.

## The oracle

Every entry is converted to an exact `Fraction`.
- **n = 1**: σ² = Σa² exactly; the square root at 256 bits or more.
- **n = 2**: G = AᵀA exactly; disc = (g11 − g22)² + 4g12² and det = g11·g22 − g12² exactly;
  λmax = (tr + √disc)/2 (no cancellation) and λmin = det/λmax, σ = √λ, at mpmath precision
  P = 256. Both σ then carry a relative error of at most 2^(−P+3), however small σ₂ is.
  det = 0 means σ₂ = 0 exactly.
- **n ≥ 3**: the exact rank r comes from fraction-free Bareiss elimination on the integer-scaled
  matrix, and the n − r smallest σ are exactly 0. The r non-zero σ come from `mpmath.svd_r` at
  precision P ≥ max(192, 140 + the spread of the entries' exponents, 140 + log2(σ₁/σ_r)) bits,
  run twice, at P and at P + 64. The two runs must agree to the a-priori bound 2^(−P+20)·σ₁
  (backward stability plus Weyl).
- **Rounding**: each σ is rounded once, correctly (ties to even, subnormals, overflow to +inf),
  from an exact Fraction, by CPython's correctly rounded int/int division. A σ is accepted
  (`rel_ok`) only when its whole uncertainty interval rounds to the same double: relative
  2^(−P+4) for n ≤ 2, absolute 2^(−P−44)·σ₁ for n ≥ 3. Otherwise the precision is raised.

Every σ of the corpus is certified: `rel_ok` is true everywhere, with no inconsistent pair of
runs (`corpus.py` prints both counts). Exact zeros count as certified. Every non-zero 1- and
2-column matrix needed 256 bits; the most was 853 bits for `graded` and 2268 for `extreme`.
408 `rand2` matrices have an exact σ₁ above DBL_MAX, so their correctly rounded σ₁ is +inf.
`tools/orcstat.py` prints these per class, for any set.

**Caveat.** The n ≥ 3 certificate assumes that `svd_r`'s backward error is within 2^20 ulps of P
bits times σ₁. That is not proven here, but several checks support it:
- the runs at P and P + 64 agree;
- Σσ² matches ‖A‖²_F (exact) to 2.1e−76 relative, and for square full-rank A, ∏σ matches
  |det A| (exact) to 1.3e−62 (`corpus.py` prints both);
- `oracle_xcheck.py` recomputes 492 sampled n ≥ 3 matrices (60 each from `sqdef`, `talldef`,
  `outer`, `randwell`, `graded`, `extreme`, `rankdef` and `cluster`, and the 12 witnesses with
  n ≥ 3) by independent routes: the exact rank by Gaussian elimination modulo the primes
  2^61 − 1, 2^89 − 1 and 2^107 − 1 (each gives a lower bound, exact unless the prime divides
  every r×r minor), and the σ by `eigsy` of the exact Gram matrix at P = 2·log2(σ₁/σ_r) + 200
  bits, where the n − r smallest eigenvalues must lie within 2^(−P+20)·σ₁² of 0 and the r-th
  more than 2^64 times that above it. It agrees on all 492: the rank, and every σ bit for bit.

`corpus.py` also checks itself, and exits with status 1 when a check fails (keeping the new
files as `*.failed`, above):
- the exact bits quoted in the issue for A1…A6, B1, B2, C and Z;
- W54's decimal σ at all four scales;
- numpy's `svd` against the oracle on 200 random matrices (worst 2.62 u·σ₁; it must stay ≤ 10).

## The driver

- `driver.cyr` reads the whole corpus into an anonymous mapping outside the bump heap, and
  buffers its output in another.
- Per matrix it copies A into a fresh `ganita_mat_new`, poisons U, Vt and S, and calls
  `ganita_mat_svd`. The values-only call gets a fresh copy of A and a poisoned S2.
- **Memory**: `lib/alloc.cyr` has no mark and release, only `alloc_reset()`, which rewinds the
  heap and zeroes the part used since the last reset (all of the first chunk after a spill). The
  driver calls it after every matrix, which is safe because the corpus and the output live
  outside the heap. The maximum RSS is 14 MiB with the reset and 56 MiB without it (1.2.12; a
  driver built with `DRIVER_FLAGS="-D SVDH_NO_RESET"`), measured with this snippet, which is not
  a harness script:

  ```sh
  python3 - build/svdh/build/driver_cur build/svdh/corpus.bin <<'EOF'
  import resource
  import subprocess
  import sys
  subprocess.run([sys.argv[1]], stdin=open(sys.argv[2], 'rb'), stdout=subprocess.DEVNULL, check=True)
  print(resource.getrusage(resource.RUSAGE_CHILDREN).ru_maxrss // 1024, 'MiB')
  EOF
  ```
- A candidate that caches a heap pointer in a global across calls would be broken by the reset.
  Build such a candidate with `DRIVER_FLAGS="-D SVDH_NO_RESET"`. On 1.2.12 the results are
  bit-identical either way.
- stderr reports the matrix count, and how many calls modified A (`adv/driver_rcp.cyr`: in how
  many matrices a call did; it compares A once, after all five calls). It must be 0: `run.sh`,
  `adv/run.sh` and `hunts/run.sh` exit 1 when it is not, or when a driver prints no such count
  (after scoring the results).

`bench.cyr` times seven cases (random 3×3 to 60×30, a zero-row 10×10, a rank-15 20×20), the
full and the values-only call. Each batch is calibrated to at least 25 ms, and it prints the
median and the minimum over 9 batches, in ns per call. `alloc_reset()` runs after every call,
inside the timed loop. Timings move by a few percent from run to run: to compare two trees, pin
one core (for example `taskset -c 3 scripts/svdh/bench.sh . cur`) and interleave several runs of
each.

## Metrics and PASS (check.py)

u = 2^−52, and σ̂ is the exact σ (`hp`). All arithmetic is in numpy longdouble (80-bit x87 on
x86_64; binary128 on aarch64 Linux), so the metrics themselves are good to about 2^−10 u. Where
longdouble is plain double, the scorers refuse to run: σ̂ above DBL_MAX would become +inf, and
the metrics would be good to about 1 u only.

| metric | definition |
|---|---|
| `sig_nw` | max_i \|σ_i − σ̂_i\| / (u·σ̂₁ + 2^−1074), in u. A returned double equal to the correctly rounded oracle counts as 0, +inf included |
| `sig_rel` | max over the i with `rel_ok` and σ̂_i > 0 of \|σ_i − σ̂_i\| / ulp(σ̂_i), in ulps of the double format (2^−1074 at least) |
| `desc` | σ descending, ≥ 0, no NaN (−0 allowed) |
| `vt_orth` | max \|Vt·Vtᵀ − I\| / u |
| `u_orth` | max \|U_Jᵀ·U_J − I\| / u over the columns J whose **returned** σ_j ≥ 2^−1022 |
| `u0col` | every column j with returned σ_j = 0 is all zero in U (ganita's convention; reported, not part of PASS) |
| `recon` | max_ij \|A − U·diag(σ)·Vt\| / (u·σ̂₁ + 2^−1074). It is n/a (`rec_na`) when a returned σ is not finite and the exact σ₁ itself rounds to +inf |
| `vo` | the values-only status equals the full one, and its σ bits are identical |

Metrics are computed for status-0 results only. A NaN metric (from poison or NaN output) counts
as +inf.

**PASS** = status 0 AND `sig_nw` ≤ 4·max(1, √(mn)/2) AND `u_orth` ≤ 256 AND `vt_orth` ≤ 256 AND
(`recon` ≤ 16·max(1, √(mn)), or n/a as above) AND `desc`. For `nonfinite`, PASS = both statuses
< 0, and the report also counts the refusals that left every out-param poisoned.

`sig_rel` is not part of PASS. Where σ lies far below u·σ₁ (`outer`, `rankdef`, `cluster`, the
`rand2` spreads of 600 and 2100) no backward-stable method determines it relatively, and the
metric is huge by nature. It means most on `fam`, `randwell`, `talldef`, `graded` and `extreme`.

`u_orth` leaves out the columns of subnormal σ. `tools/allorth.py` measures U over every non-zero
σ, which is what `_linalg_svd_reorth` is for.

The output of `check.py`:
- per class: the status split (−1, −2, −3, other), PASS, and the `desc`, `u0col` and `vo`
  violations;
- the worst value and the 99.9th percentile (`method='higher'`) of each metric;
- with `--sub`, the same per subclass (shape, edit, spread, each witness);
- the failing matrices: status 0 but not PASS, worst first after normalising by the PASS
  thresholds (`nw` is `sig_nw`, `rel` `sig_rel`, `uo` `u_orth`, `vt` `vt_orth`, `rec` `recon`),
  then samples of status ≠ 0;
- the worst matrix id per metric;
- `--json out.json` writes all of it, plus per-matrix status, PASS and metrics, and the failing
  ids per class.

The corpus, meta and oracle default to `build/svdh`; `--corpus`, `--meta` and `--oracle` score
another set. `--top N` (N ≥ 0, default 8) sets how many failing matrices are listed per class.
`--diff` reads only the corpus, the meta file and the two results files, and refuses
`--oracle`, `--baseline`, `--json` and `--sub`.

`gen.py` without `--classes` builds `adv`, every class except `bm3`, `reprows` and `rgfail`.
`cycle` reads `hunt_hits.json`, a snapshot of the 76 hunt hits the set was built from. With
`--hits DIR` it reads `DIR/*.json` instead, which is what `hunt.py` writes: run the hunt on a
candidate, then score its hits alone against the exact oracle with
`gen.py --classes cycle --hits build/svdh/hunt_hits --out <name>` (without `--classes cycle`
that would rebuild all of `adv` too). `hunt.py` adds its hits to the seed files already in
`build/svdh/hunt_hits`, from every earlier hunt and every label (the `hunt_all.sh cur` run below
included), and `gen.py` reads them all: remove that directory before the candidate's hunt, or
run it in a fresh `SVDH_WORK` (with its own `build.sh`), and give `hunt.py` the candidate's label
alone. Hits that `why` only flags as `nw` are skipped, since numpy's own σ can be tens of u off
(the `nw_sample` below), and so are repeats; `cycle` keeps the first 400 of the rest and warns
when there are more. A hit file that is not a list of hits, or holds a NaN or infinite entry,
stops `gen.py` with a message.

1.2.12 passes `adv` 3734 / 3734 and `adv2` 75 / 75, with no status other than 0. On `adv` the
worst values are `sig_nw` 23.4 u (`bigdef` 300×300, against numpy's σ, which is all that

- `adv2`: none of the failure checks fire (rank(A, 0) exceeds the exact rank on 8, which is
  expected; see below).
- `adv`: 12 subnormal σ returned as 0 [142]. 53 normal σ that `kappa` says are relatively
  determined are off by more than 64·m·n·κ·u, in 27 matrices [127 in 75], by 0.0476% to 372%.
  Every one is in a row-graded matrix spanning 1,900 to 2,030 binades: `subgrad` with rows from
  2^1000 down to 2^−1000 or 2^−1030, and the `rowgradbig` 30×30 over 1,900.
- rank, condition and pseudo_inv on `adv`: rank(A, 0) falls below the exact rank on 55 matrices
  [173], and never exceeds n. (It exceeds the exact rank on 563 [314], which is expected: on
  exactly rank-deficient input, rounding leaves the zero σ slightly positive.)
  rank(A, tol), tol = 1e-12·σ₁, agrees with the count of exact σ above tol wherever it is
  checked [likewise], that is, where no exact σ lies within the error PASS allows a returned σ,
  4·max(1, √(mn)/2)·(u·σ₁ + 2^−1074), of tol (a result that passes may put such a σ on either
  side). That leaves 199 [166] matrices unchecked, and rank disagrees with the exact count on 25
  [25] of them, all `ulpcols` whose every exact σ is subnormal: there tol rounds to 0, the exact
  count includes a σ that itself rounds to 0, and in each of the 25 [25] rank returns the count
  of correctly rounded exact σ above tol, the best a double result can give. Condition disagrees
  on 51 [51] (`subonly`, `ulpcols`, `ties`), all in matrices whose every exact σ is subnormal,
  where it cannot be checked to that resolution: the exact σ_n, correctly rounded, is a subnormal
  of at most 19 significant bits (2^−1074 itself in 22 of the 51), short of the condition check's
  1e-6 relative tolerance.
  No pseudo_inv is beyond its Penrose bound [0]. That check skips the 257 [223] pseudo_inv with
  a non-finite entry: in each, ‖A⁺‖₂ = 1/σ_k (σ_k the smallest σ above 1e-12·σ₁) is above

  the range, not the harness's.

## The hunts

### Oracle-free (adv/hunt.py)

`hunt.py SEED COUNT --labels L1[,L2…] [--fam f1,…]` draws COUNT matrices from ten seeded families:

| family | contents |
|---|---|
| `cyc` | small dense matrices with a moderate exponent spread, then a random power of two |
| `int` | small-integer matrices: exact ties, cancellations, rank deficiency |
| `tall2` | tall two-column matrices whose dot products need heavy rounding, nearly orthogonal |
| `full` | entries over the whole double range, subnormals included |
| `def` | zero rows, repeated rows, duplicated columns, at a random power-of-two scale |
| `grad` | graded by row, by column or both, over up to 2000 binades |
| `nearpar` | a tiny column nearly parallel to a big one |
| `hadp` | Hadamard-like columns with one-ulp perturbations and exact scalings |
| `eqn` | tall equal-norm columns at cosines of a few u |
| `subrow` | one or two normal rows over subnormal rows |

It runs each label's `build/svdh/build/drv_<L>` (from `adv/build.sh`; a `_a64` driver under
qemu-aarch64) and flags, per tree:
- a status other than 0, or a values-only status that differs;
- for status 0: non-finite or non-descending σ, U or Vᵀ more than 256 u from orthonormal,
  `recon` over 16·max(1, √(mn)), or σ more than 4·max(1, √(mn)/2) + 8 u from numpy's.

Each flagged matrix is added to `build/svdh/hunt_hits/seed<SEED>.json` (written under a temporary
name and renamed), which keeps the hits of every earlier hunt of that seed, of every label.
`hunt.py` reads that file again, under a lock on the directory, just before it writes, so hunts of
the same seed that run at the same time (one per tree, say) keep each other's hits. Several labels
in one run cost less, since the matrices are drawn once. A driver that exits non-zero or writes
other output than the matrices' records is reported on a `DRIVER FAILED` line with the number of
matrices it completed, and `hunt.py` exits with status 1. The first matrix from there on that makes
the driver fail on its own is saved as a hit (why `driver exit N`, or `driver output B bytes, E
expected` for one that exits 0); when the driver completed every record, so that the failure is at
its exit or in output past the records, only the first matrix is tried alone, and the line says so.
The `seed … matrices` line counts the matrices kept (those drawn, less the non-finite ones it
skips), and a tree's `status` line only those its driver completed, so neither shows such a
failure: the `DRIVER FAILED` line and the exit status do. `hunt.py` names its scratch files (under
`build/svdh/hunt`) by its process id, and removes them also when it fails or is stopped by SIGINT
or SIGTERM, which stop the running driver too (the driver, or `qemu-aarch64`, replaces the shell
that starts it with its times file on fd 3, so that it is the process killed). A missing driver, a
malformed hit file or a hit directory it cannot write stops it with status 2.

`hunt_all.sh <label>` runs the 1.2.12 schedule, 10 at a time:
- seeds 101–116 × 20,000 and 201–206 × 30,000 over every family;
- 301–308 × 20,000 of `eqn`;
- 401–408 × 20,000 of `subrow`.

That is 820,000 draws; 2 (in seed 115) come out non-finite and are skipped, which leaves
819,998. Logs go to `build/svdh/hunt_logs/s<seed>.log`, and each log names its matrix count and
the status counts per tree, and ends with `hunt.py exit N`. `hunt_all.sh` removes the
schedule's old logs first, and exits 1, naming the seeds, when a seed's `hunt.py` did not exit
0 (a driver failed, or `hunt.py` itself did) or its log has no status line or a `DRIVER FAILED`
line. It takes a few minutes. It must exit 0; only then do the counts below cover every matrix.
In a fresh `build/svdh` (the hits are added to those of earlier hunts):

```sh
scripts/svdh/adv/build.sh cur
scripts/svdh/adv/hunt_all.sh cur && echo ok                                         # ok
grep -l 'DRIVER FAILED' build/svdh/hunt_logs/*.log                                 # empty
grep -h 'matrices' build/svdh/hunt_logs/*.log | awk '{ n += $3 } END { print n }'   # 819998
grep -h 'status {' build/svdh/hunt_logs/*.log | grep -v 'status {0: [0-9]*}'      # empty: all status 0
python3 scripts/svdh/tools/hitstat.py                                              # the hits, below
```

On 1.2.12 all 819,998 are status 0. 21,544 are flagged, every one for `nw`, the distance to
numpy's σ, which is not exact. The 21,540 flagged for `nw` alone are all `eqn` matrices (tall,
equal-norm columns at cosines of a few u), so `adv/nw_sample.json`, 150 of them picked at
random (by ad-hoc code, not carried here; the file is the snapshot), is all `eqn`; its labels and
`tree` say `cur`, as `hunt_all.sh cur` writes them. Scored against the exact oracle, all 150
pass, with σ within 3.32 u·σ₁ (`sig_nw`):

```sh
python3 scripts/svdh/hunts/mkwit.py scripts/svdh/adv/nw_sample.json   # -> build/svdh/hunts/nw_sample
scripts/svdh/hunts/run.sh nw_sample cur
```

Four are also flagged `nonfinite S` (two of them `rec` too): `full` matrices whose exact σ₁ is
above DBL_MAX, so +inf is the correctly rounded answer, and all four pass against the exact
oracle:

```sh
python3 scripts/svdh/tools/hitstat.py --select 'nonfinite S' --out build/svdh/nonf.json
python3 scripts/svdh/hunts/mkwit.py build/svdh/nonf.json      # -> build/svdh/hunts/nonf
python3 scripts/svdh/tools/orcstat.py hunts/nonf              # s1=inf: 4
scripts/svdh/hunts/run.sh nonf cur                            # PASS 4 / 4
```

`adv/tall_study.py --labels L1[,L2…] [SEED [MS [NS [REPS [KINDS]]]]]` prints U and Vᵀ
orthonormality and σ_n/σ₁ for tall matrices, one column per tree (`--help` lists the kinds).

### With an exact oracle (hunts/)

`hunts/gen.py --out DIR --set f1,f2,…` builds a set from families aimed at specific edges (each
family at most once), with an exact oracle. Where the generic one is too slow it uses structural
oracles: the union of the blocks' σ, σ² known in closed form, or `eigsy` of the exact Gram matrix.
The Gram oracle also stands in where `mpmath.svd_r` does not converge (a `RuntimeError`), which
`gen.py` reports on stderr, naming the matrix: once in the five sets below, for id 478 of `s2`,
`hadamard dup-row 32x32 e=-1020` (method `gram`; its `oracle.json` entry holds σ as in closed form:
2^−1017, then 4√2·2^−1020 thirty times, then 0). Each family draws from `random.Random(20261004 +
the sum of its name's character codes)`. The five sets that were run on 1.2.12, rebuilt byte for
byte by these commands (`gen.py` prints the counts; checksums under [Hunt-set
checksums](#hunt-set-checksums)):

```sh
python3 scripts/svdh/hunts/gen.py --out s1 --set shiftdown,dblmax,allsub,checker,ties,sperm   # 994
python3 scripts/svdh/hunts/gen.py --out s2 --set blockdiag,hadamard,tri,illcond,mixedrange   # 906, about 4.5 min
python3 scripts/svdh/hunts/gen.py --out s3 --set tall,randtall                               # 83
python3 scripts/svdh/hunts/gen.py --out s4 --set kahan                                       # 32
python3 scripts/svdh/hunts/gen.py --out s5 --set boundary                                    # 563
scripts/svdh/hunts/run.sh s1 cur        # needs build/svdh/build/driver_cur, from run.sh . cur
scripts/svdh/hunts/run.sh s1 cur_a64    # driver_cur_a64 (run.sh . cur aarch64) under qemu; exits 1 if it differs from res_cur.bin
```

On 1.2.12 the aarch64 results of every hunt set (and of `nw_sample` above, and `wshift` and
`wshift2` below) are bit-identical to the x86_64 ones.

| set | families | 1.2.12 |
|---|---|---|
| `s1` | `shiftdown` (A's largest entry near DBL_MAX over blocks near DBL_MIN), `dblmax`, `allsub`, `checker`, `ties`, `sperm` (signed permutations, [I; I]) | PASS 994 / 994 |
| `s2` | `blockdiag` (blocks at wildly different scales, permuted), `hadamard`, `tri` (triangular, graded diagonals), `illcond` (Hilbert, Vandermonde), `mixedrange` | PASS 906 / 906 |
| `s3` | `tall` (one to six columns, up to 100,000 rows), `randtall` | PASS 83 / 83 |
| `s4` | `kahan` | PASS 32 / 32 |
| `s5` | `boundary`: σ₁ within a few ulps of DBL_MAX | PASS 556 / 563 |

The 7 that fail in `s5` return σ₁ = +inf (check.py lists them with `nw inf` and no
`NOT-DESC`) where the correctly rounded σ₁ is finite, DBL_MAX or one or two ulps below it
(`0x7FEFFFFFFFFFFFFF`, `…FE` or `…FD` in the set's `oracle.json`). σ₁ is unscaled by one
rounding from a value with the usual error of a few ulps, and past DBL_MAX that rounding goes to
+inf. `ganita_mat_svd`'s comment documents this edge.

`hunts/mkwit.py wshift|wshift2|FILE.json [--out DIR]` builds a small set from explicit bit lists
(FILE.json in the hunt-hit format; a NaN or infinite entry is refused). `wshift` and `wshift2`
hold inputs whose largest entry is near DBL_MAX. The working copy is then scaled down, and a
column of X whose σ lies a few binades above 2^−1022 becomes all subnormal. For n ≥ 4, a U built
from such columns comes out far from orthonormal, unless `_linalg_svd_reorth` repairs it.
Without that repair, measured by check.py's `u_orth` (the columns whose σ ≥ 2^−1022), `wshift`
holds four of the worst of its generator's 2,800 matrices (329, 261, 228 and 204 u; the 1st,
3rd, 5th and 8th), one each at 8×5, 8×4, 6×4 and 5×5, and `wshift2` the two worst 4096×4 of 40
(529 and 516 u). Over every non-zero σ, which is what the repair is for, the same generators
reach far more without it, 17,277 u (a 4×4) and 5,359 u, and by that measure the `wshift`
witnesses rank only 133rd to 216th and the `wshift2` ones 12th and 13th (`tools/d1hunt.py`
measures that, `u_all`, on 2,275 inputs of this kind). `mkwit.py --rank` prints these figures
from a tree without the repair:

```sh
mkdir -p build/svdh/noreorth && cp -r src build/svdh/noreorth/ && ln -s "$PWD/lib" build/svdh/noreorth/lib
sed -i 's/^\( *\)_linalg_svd_reorth(y, rows, cols, r, sig);$/\1# _linalg_svd_reorth call removed/' \
    build/svdh/noreorth/src/linalg.cyr
grep -c '_linalg_svd_reorth(y, rows, cols, r, sig);' build/svdh/noreorth/src/linalg.cyr   # 0
scripts/svdh/run.sh build/svdh/noreorth noreorth        # still PASS 20622 / 20622
python3 scripts/svdh/hunts/mkwit.py wshift --rank noreorth
python3 scripts/svdh/hunts/mkwit.py wshift2 --rank noreorth
```

The witnesses are regenerated from their seeded generators and picked by label, so building the
sets needs no driver. check.py's `u_orth` skips subnormal σ, so measure them with `allorth.py`:

```sh
python3 scripts/svdh/hunts/mkwit.py wshift
python3 scripts/svdh/hunts/mkwit.py wshift2
scripts/svdh/hunts/run.sh wshift2 cur
python3 scripts/svdh/tools/allorth.py build/svdh/hunts/wshift2/res_cur.bin \
    --corpus build/svdh/hunts/wshift2/corpus.bin --meta build/svdh/hunts/wshift2/corpus_meta.json
```

On 1.2.12 both sets pass, with U at most 1.9 u from orthonormal over every non-zero σ
(`allorth.py`; 0.91 u on `wshift2`, 1.9 u on `wshift`).

## Tools

- `tools/d1hunt.py <label>` runs `build/svdh/build/driver_<label>` (from `run.sh`) on 2,275
  matrices of the `wshift` kind: the largest entry near DBL_MAX, σ near or below DBL_MIN,
  n ≥ 4, from 4×4 to 96×96 and up to 4096 rows. It reports, per subfamily, the status,
  `u_orth` and `u_all` (U over every non-zero σ), Vᵀ, `recon` against the returned σ₁, `vo!`,
  `nonf` (matrices with a non-finite output), `u0c!` (the zero-column rule) and `desc!` (σ not
  descending, or a NaN). A NaN in U or Vᵀ makes its metric +inf; `recon` is undefined where a
  returned σ is +inf and counts as 0 there, while a NaN or −inf σ makes it +inf. It then breaks
  the non-finite output down: per matrix, how many σ are +inf and whether they lead, any other
  non-finite σ, non-finite U or Vᵀ. And it holds each +inf σ against numpy's σ of A·2^−64, which
  must lie above the rounding threshold DBL_MAX + ulp/2 by more than 2^−40·σ₁ (2^12 u, far
  beyond numpy's error) for +inf to be the correctly rounded value. On 1.2.12 every matrix is
  status 0, `u_all` is at most 5.21 u and `desc!` is 0. 634 have a non-finite output, each the
  leading σ as +inf: σ₁ alone in 595, the two largest in 35, the 8 to 10 largest in 4 (`F5`).
  U and Vᵀ are finite in all 634, and numpy puts all 701 +inf σ above the threshold by more than
  the margin (and no finite σ).
- `tools/allorth.py RESULTS [--corpus C --meta M]`: the worst U orthonormality over every
  non-zero σ, per class (a NaN counts as +inf), and the count of U columns that are not all zero
  although their returned σ is 0. Only status-0 results are measured; the others are counted per
  class on a line of their own (on the 1.2.12 corpus, the 18 `nonfinite`).
- `tools/cmpres.py NEW OLD [--corpus C --meta M --oracle O] [--show N]`: the matrices whose bits
  differ between two results files, with their metrics side by side. Status changes are counted
  on their own; better / worse / same compare `u_orth` where both results have a number (a
  metric is NaN where the status is not 0) and both pass `desc`. `u_orth` leaves out the column
  of a NaN σ, so a result that turned a σ into NaN could otherwise count as better: a matrix
  whose σ are not descending, or hold a NaN, in either result is counted on its own (`desc`
  lost, gained, failed in both). The worst values ignore NaN; the listing shows the matrices that
  lost PASS first, then the rest by the larger of the two `u_orth`. A label too long for its
  column ends in `...` (as in check.py and report.py).
- `tools/orcstat.py [DIR]`: per class of a set's oracle, the methods, the precision used (n ≤ 2
  and n ≥ 3; the methods `zero` and `blocks` record none and are left out, and counted on the last
  line), the uncertified σ, the matrices of exact rank below n and those whose correctly
  rounded σ₁ is +inf. DIR is a directory, or a set under `build/svdh` (`adv`, `hunts/s2`); the
  default is the corpus.
- `tools/hitstat.py [DIR|FILE.json …] [--select REASON --out FILE.json]`: hunt hits per tree
  and per family and reasons (default `build/svdh/hunt_hits`); `--select` and `--out` also write
  the hits with one reason to a file that `hunts/mkwit.py` takes. On the 1.2.12 hunt: 21,540
  `eqn` hits for `nw` alone, 2 `full` for `nonfinite S` and `nw`, 2 `full` for `nonfinite S`,
  `nw` and `rec`.
- `tools/quick.py` is a module: `quick.run(items, driver)` writes a corpus from
  `(label, m, n, bits)` items, runs a driver, and returns the oracle-free metrics per matrix
  (`u_orth`, `u_all`, `vt_orth`, `recon` against the returned σ₁, status, `vo`). A metric that a
  NaN in U or Vᵀ makes NaN is +inf, as in check.py; `recon` is NaN only where a returned σ is not
  finite. It raises a `ValueError`, naming the item, unless each has m ≥ n ≥ 1 and m·n 64-bit
  words. Scratch files go to `build/svdh/scratch` and are removed afterwards; a driver that
  fails, or writes another number of bytes than the items need, raises a `RuntimeError`. Run as
  a script, it prints its usage for `-h` and `--help`. Like check.py's `u_orth`, its `u_orth`
  leaves out the column of a NaN σ (`u_all` keeps it, and `desc` is false then).

## Not carried here

- **Instrumented drivers.** Sweep counts and branch counters (how often each special branch fires,
  "at most 7 sweeps") need a copy of `src/linalg.cyr` with counters added, and are not part of
  this harness. `report.py` prints a sweeps section only when `inst_<L>.bin` files exist, and
  `quick.run(..., inst=True)` reads 14 counters per matrix from such a driver.
- **The row-graded sweep study** (181 row-graded D·B, 30×30 to 200×200) needs the same
  instrumented driver.
- **Three 2^20×5 of the `wshift` kind** (the largest entry near DBL_MAX, σ near or below
  DBL_MIN), which `ganita_mat_svd`'s comment counts among the inputs that come back with status 0:
  no generator here builds them; `tools/d1hunt.py` stops at 4096 rows.
