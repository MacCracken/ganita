# ganita v1.2.3 — P(-1) hardening sweep

**Date**: 2026-09-07
**Version audited**: 1.2.2 (repo HEAD `b025153`) → shipped as **1.2.3**
**Toolchain**: cyrius `6.6.0`, pin unchanged from 1.2.1
**Method**: seven independent audit lenses over `src/`, each adversarially
verified by a second pass whose default posture was *refuted*. **Every finding
below was reproduced by a program that was built and run** — 90 survived
verification, 0 were refuted outright, 6 were downgraded and 3 upgraded.

---

## The shape of it

ganita's defect profile turned out to be strikingly uniform. Of 90 confirmed
findings, the single largest class — and every one of the memory-safety ones —
is the same sentence repeated across the API:

> **A function derives its loop bounds from one argument and never looks at the
> others.**

`mat_mul` took its inner dimension from `cols(A)` and never read `rows(B)`.
`mat_add` and `mat_sub` took their shape from A and read B for `rows(a)*cols(a)`
words regardless of B's real size. `mat_lu`, `mat_det`, `mat_inv`,
`mat_cholesky` and `mat_trace` took `n` from the **row** count and then indexed
an `n × n` region of a store holding `rows*cols`. `set_row` and `set_col`
accepted any index. `submatrix` checked the *sign* of the extent but never the
window against the source. `least_squares`, `svd`, `rank`, `condition` and
`pseudo_inv` documented `m >= n` and enforced nothing.

In every case both arguments were matrices `ganita_mat_new` had accepted. At
small sizes the result was a well-formed matrix containing a neighbouring
allocation's bytes reinterpreted as f64 — no null, no error code, nothing to
notice. At large sizes it was SIGSEGV. That combination is the worst of both: it
does not fail in testing and it does fail in production.

**This is the same defect 1.2.2 fixed in one place.** The `least_squares` null
write naad filed was an unchecked *allocation*; these are unchecked *arguments*.
Both come from the same habit, and 1.2.2 closed one instance of it. This sweep
closed the class.

A second, smaller theme is worth naming because it is subtler:

> **Every f64 comparison is false against a NaN, so a guard written as
> `if (bad) { return failure; }` falls through and reports success.**

That is how `ganita_mat_eq` came to report an all-NaN matrix as **equal to the
identity** — and `mat_eq` is the comparison tool this project's own test suite
uses to check its decompositions. A solver that returned NaN would have been
certified correct by the suite that exists to catch it. It is the most
consequential finding here and the least visible.

## Fixed in 1.2.3

The test suite went from **260 to 322 assertions**. Every fix below has at least
one assertion covering the specific path that used to fail.

### Memory safety — the out-of-bounds class

| Function | Was | Now |
|---|---|---|
| `mat_mul` | inner dim from `cols(A)`; `rows(B)` never read | `0` when `rows(B) != cols(A)` |
| `mat_add` / `mat_sub` | shape from A; B read at A's dimensions | `0` on shape mismatch |
| `mat_set_row` / `set_col` | any index accepted — **out-of-bounds write** | `-2` outside `[0, rows)` / `[0, cols)` |
| `mat_row` / `mat_col` | any index accepted | `0` outside range |
| `mat_submatrix` | window never checked against the source | `0` for a window past the source or a negative origin |
| `mat_trace` | `n` from row count; diagonal walk past the store | NaN for non-square |
| `mat_lu` / `det` / `inv` / `cholesky` | `n` from row count; `n × n` over a `rows × cols` store | `0` / NaN / `0` / `0` for non-square |
| `gaussian_elim` | indexes column `n`; an `n × n` argument wrote past the store on every row | `0` unless the input is `n × (n+1)` |
| `least_squares` | back-substitutes from `cols-1`; a wide design read past `qtb` and `R`, then returned **success with NaN** | `-2` for `m < n` |
| `eigen_sym` | wrote `rows - cols` elements past its working copy for a non-square | `-2` for non-square or a mis-shaped `out_vecs` |
| `svd` / `rank` / `condition` / `pseudo_inv` | `m >= n` documented, unenforced | `-2` / `-2` / NaN / `0` for wide input |
| every function above | a null argument was dereferenced | null gates throughout |

**Note what the preconditions did to the 1.2.2 allocation checks.** Adding
`m >= n` and the square requirements makes most of the cap-driven allocation
failures *structurally unreachable* — the only inputs that produced them are
exactly the inputs now rejected, and for a square input the `n × n` working
factor cannot exceed the cap when the input itself did not. The allocation
checks all remain and still guard genuine out-of-memory; there is simply no
longer a legal argument that reaches them through the element cap. The suite now
records that, rather than the weaker thing it used to assert.

### Correctness

- **`mat_eq` and `mat_is_symmetric` now fail closed on NaN.** See above.
- **`mat_cholesky` rejects positive-*semi*-definite input.** The pivot guard was
  `diag < 0`, strictly less than, so a pivot of exactly zero passed,
  `sqrt(0)` went onto L's diagonal, and every later off-diagonal divided by it.
  `[1 2; 2 4]` — symmetric, det 0, eigenvalues 0 and 5 — returned **1**, produced
  `L = [1 0; 2 0]`, and `cholesky_solve` then returned **0 (success)** having
  written **NaN** into every slot. A caller doing exactly the documented thing
  got *success, success, NaN*. Now `<= 0`, with NaN rejected explicitly.
  `cholesky_solve` additionally refuses a factor with a zero diagonal, since it
  takes L from the caller and cannot know where it came from.
- **`ganita_f64_asinh` was only correct for `x >= 0`.** asinh is odd, but
  `ln(x + sqrt(x²+1))` at a negative `x` subtracts two nearly equal quantities
  and the significant digits cancel. Below about `-2^26` the sum rounded to 0 and
  the answer was `-inf`; below `-1.34e154` the `x*x` overflowed first and the
  answer came back **`+inf` — wrong in sign as well as magnitude**. It also
  returned exactly `0.0` for every `|x| <= 1e-17`, because it computes
  `ln(1 + tiny)` as `ln(1.0)`. Now computed on `|x|` and re-signed, with a
  small-argument and a large-argument regime. `asinh(1e18)` is `42.139678854453`
  against a true `42.13967885445277`; oddness holds **bit-exactly** in all three
  regimes.
- **`ganita_binomial` wrapped i64 silently from `n = 62`.** Its own comment
  claimed it used "symmetry + iterative multiply to avoid overflow" — symmetry
  halves the multiplies and does nothing about the size of the answer. It now
  tests `result > INT64_MAX / factor` before each multiply and returns `-1`
  rather than a plausible wrong count. `binomial(61,30)` is exact at
  `232714176627630544`; `binomial(62,31)` refuses. The same test bounds the loop:
  `binomial(2^62, 2^61)` used to iterate 2.3 × 10¹⁸ times — about **560 years**,
  CWE-834 — and now returns immediately.
- **`ganita_binomial` and `ganita_fibonacci` rejected negative arguments.** Both
  used to skip the loop body and return `1`.
- **`ganita_f32_sin` / `_cos` returned their argument for `|x| >= 2^63`.** The
  underlying `f64_sin` reduces only within the i64 range. Sine is bounded to
  `[-1, 1]` by definition, so returning `2^70` is not an approximation but a
  category error — and roughly a quarter of the finite f32 exponent range is
  above `2^63`. Now NaN, which propagates loudly where `2^70` propagates
  silently.
- **`svd` no longer discards a non-convergent eigendecomposition.** It tested
  only for the allocation code and reported success on singular values derived
  from a matrix that was never diagonalised. Any negative is now a failure.
- **`rank` rejects a negative or NaN tolerance.**

### Optimization

- **`ganita_mat_eigen_sym` is O(n³), was O(n⁴).** Classical Jacobi picks the
  largest off-diagonal entry each time; through 1.2.2 that meant rescanning the
  whole upper triangle — O(n²) — before **every** rotation, and convergence takes
  O(n²) rotations. `rank`, `condition` and `pseudo_inv` all route through it, so
  the cost was not confined to callers who wanted eigenvalues.

  A per-row maximum index makes the global search one O(n) pass; after a rotation
  at `(p, q)` rows `p` and `q` are recomputed in full and every other row is
  repaired from its two changed entries, rescanned only when its recorded maximum
  *was* at column `p` or `q`.

  Ties break identically, so **the pivot sequence is unchanged** — verified by
  running both implementations in one process on identical matrices:

  | n | 1.2.2 | 1.2.3 | speedup | rotations | eigenvalues |
  |---|---|---|---|---|---|
  | 8 | 109 µs | 118 µs | 0.9× | identical | bit-identical |
  | 40 | 25.4 ms | 13.7 ms | 1.9× | identical | bit-identical |
  | 120 | 1.55 s | 0.36 s | 4.3× | identical | bit-identical |
  | 200 | 11.53 s | 1.76 s | **6.5×** | identical | bit-identical |

  Below about n = 20 the index bookkeeping costs slightly more than the scan it
  replaces. That is the honest trade and it is recorded in the benchmark comment.
  Three `eigen_sym` sizes are now in `tests/ganita.bcyr` so a regression to O(n⁴)
  shows up as the largest size pulling away.

### Contracts and hygiene

- **`ganita_mat_dot`'s doc blessed a shape it cannot read.** It said "Nx1
  matrices or flat arrays"; the body reads `load64(a + i*8)` from the pointer
  directly, so an `N×1` matrix has its 16-byte `{rows, cols}` header read as the
  first two elements and every value shifted by two slots — a plausible wrong
  answer, no diagnostic. Doc corrected; the function is for flat arrays.
- **`src/main.cyr` omitted `src/math_f32.cyr`** while calling itself the full
  bundle, so the build gate and `cyrius vet` never saw 27 public functions.
  `vet` now reports 12 deps, was 11.
- **`GANITA_MAT_MAX_ELEMS`'s derivation comment was false.** It claimed to be
  `(ALLOC_MAX - 16) / 8` and "kept in step" — but cyrius v6.4.51 raised
  `ALLOC_MAX` from 256 MiB to **2 GiB** and the constant did not follow. That
  drift is why `least_squares`' internal `m × m` Q hit the cap at `m = 5793`
  rather than `m = 16383`, which is the SIGSEGV 1.2.2 fixed.

  **The cap was deliberately NOT raised to the re-derived 268,435,454.** Raising
  it is a capability change wearing a hardening change's clothes: one such matrix
  is 2 GiB — the entire `ALLOC_MAX` — so allocating it succeeds only by leaving
  nothing for the working factors every decomposition needs; the eigensolver is
  O(n³) so matrices near the cap are computationally out of reach anyway; and it
  silently multiplies by 8 the memory a single call can demand of every existing
  consumer. The comment now says it is a policy limit rather than a derivation.
  Raising it is tracked below.

  *This was tried and reverted during the sweep, which is worth recording:
  raising the cap turned three of the 1.2.2 allocation-failure assertions into
  real 268–512 MB allocations, one of which then fed a 6000 × 6000 matrix to the
  Jacobi eigensolver and hung the suite.*
- **`ganita_mat_eq`'s doc told callers to pass `LINALG_EPS` as the default.**
  `LINALG_EPS` is lazily initialised and reads `0` until some decomposition has
  run, so the identical call answered differently depending on what the program
  did before it. The doc now says to pass the tolerance you mean.
- **`mat_get` / `mat_set` are documented as unchecked by design**, with the
  consequences stated (CWE-125 read, CWE-787 write, and `r*cols + c` can itself
  wrap i64). They sit in every inner loop in `linalg.cyr`; a per-element branch
  there is measurable where a per-call one is not. See `SECURITY.md`.
- **A failure vocabulary is now stated once**, at the top of `linalg.cyr` —
  see [ADR 0001](../adr/0001-failure-vocabulary.md). `eigen_sym`'s
  non-convergence code moved `-1` → `-3` to fit it.

### Documentation and examples

`README.md` claimed **"Status: 1.0.0"** and its module table omitted the entire
27-function f32 tier; the documented consumption path therefore pointed at a fold
that SIGSEGVs on the case 1.2.2 fixed. `docs/guides/getting-started.md` told
readers to add features by editing `src/main.cyr`, which is a 38-line smoke test.
`docs/development/roadmap.md` was untouched `cyrius init` scaffold
(`M1 — _Title_ (v0.2.0)`) while the project sat at 1.2.2. All three rewritten.

Added: `SECURITY.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` (required by the
first-party layout; absent), `scripts/bench-history.sh` and the first
`bench-history.csv` rows, and **five runnable examples** in `docs/examples/` that
CI builds and runs on every push, so documentation that stops being true fails
the gate instead of quietly becoming a lie.

Writing those examples found two of the findings above independently — the
Cholesky semi-definite defect and the `mat_dot` doc error — which is the argument
for having them.

## Not fixed — filed, with reasons

These are real and reproduced. They are not in 1.2.3 because each needs a design
decision, an algorithm change, or a consumer-visible break that a hardening patch
should not make unilaterally.

### 1. `LINALG_EPS` is an absolute 1e-12 (HIGH)

Every singularity, convergence and rank test in the library compares an
**absolute** epsilon against a quantity whose magnitude depends on the caller's
units. Scale a perfectly well-conditioned matrix down by 1e-6 and `lu`, `det`,
`inv`, `gaussian_elim` and `condition` all call it singular while `rank` reports
full rank — the library disagreeing with itself about the same matrix. Scale up
and a genuinely singular matrix passes.

The fix is a relative test (against the matrix norm, or a pivot-magnitude
ratio), and it changes results for every existing consumer at the boundary. It
needs its own release, its own ADR, and a decision about whether the tolerance
becomes a parameter. **Filed:
[`2026-09-07-linalg-eps-absolute-tolerance.md`](../development/issues/archived/2026-09-07-linalg-eps-absolute-tolerance.md).**

### 2. SVD is computed via the eigendecomposition of AᵀA (MEDIUM)

Forming AᵀA squares the condition number, so `rank` and `condition` lose
half the available precision and start lying above cond ≈ 4e8 — while the
library's own `det`/`inv` get the same matrix right. The standard fix is a
one-sided Jacobi or Golub–Kahan SVD, which is a replacement rather than a repair.
`pseudo_inv`'s wide-matrix wrongness follows from the same root. **Filed:
[`2026-09-07-svd-via-ata-squares-condition.md`](../development/issues/archived/2026-09-07-svd-via-ata-squares-condition.md).**

### 3. QR skips reflectors on small-magnitude matrices (HIGH)

`qr` and `least_squares` compare a column's two-norm against `LINALG_EPS` and
skip the reflector when it is smaller — so a matrix whose entries are merely
*small* gets a non-triangular R and a plausible-looking wrong solution, with
`rc = 0`. The unscaled two-norm also overflows to NaN for large-magnitude
matrices, and both still return success. Both are consequences of finding 1 plus
a missing scaling step; they should be fixed together with it. **Filed in the
same issue as 1.**

### 4. f64 transcendental accuracy (MEDIUM/LOW)

`sinh`/`tanh`/`atanh` lose all significance for small `|x|` (44 % error at 1e-16,
exactly 0.0 below 1e-17) because they evaluate the cancelling form rather than a
series. `acosh` returns `+inf` above 1.34e154 where the true value is ~355;
`hypot` returns `inf`/`0` for representable hypotenuses and loses 5 significant
digits in the 1e-162…1e-154 band; `pow` is up to 47 ulps off on integer
exponents; `acos` loses ~6 significant digits near `|x| = 1`, which matters
because `acos(dot)` is this library's headline use case. Infinite arguments
return NaN across the module where C returns the correct infinity. Each needs a
series expansion or a scaled formulation — a numerics work item, not a
hardening one. **Filed:
[`2026-09-07-f64-transcendental-accuracy.md`](../development/issues/archived/2026-09-07-f64-transcendental-accuracy.md).**

### 5. f32 NaN and infinity edges (MEDIUM/LOW)

`min`/`max`/`clamp` impose a total order, so a NaN is kept or dropped purely by
its sign bit; `exp`/`exp2` (and `pow`, `atan2` by the same route) return NaN for
infinite arguments; `sign(NaN)` returns ±1.0f, turning a NaN into a finite value;
`cbrt(±inf)` returns a NaN. Also: the only correct f32 comparator (`_f32_key`) is
private, and the tier ships no `lt`/`le`/`gt`/`ge`, so consumers fall back to
exactly the raw compare the module header calls a trap. **Filed:
[`2026-09-07-f32-nan-inf-edges.md`](../development/issues/archived/2026-09-07-f32-nan-inf-edges.md).**

### 6. Remaining performance items (MEDIUM/LOW)

`pseudo_inv` spends O(n³) on an O(n²) column scaling; `mat_new` zero-fills a
buffer nine of its callers overwrite in full; `mat_get`/`mat_set` in inner loops
cost 2–3.7× over a hoisted row pointer; `rank` and `condition` run a full SVD but
read only the singular values; `sinh`/`cosh` evaluate `f64_exp` twice. All
measured. **Filed:
[`2026-09-07-performance-backlog.md`](../development/issues/archived/2026-09-07-performance-backlog.md).**

### 7. Raising `GANITA_MAT_MAX_ELEMS` — see above. Filed in the performance issue.

## ⚠ The coverage figure was inflated, and the CI gate sat on it

`cyrius coverage` credits a function when its name appears as a raw **substring**
anywhere in the scanned text, **comments included**. Every `_compat.cyr` alias
name is a proper substring of the canonical name it forwards to, so testing
`ganita_mat_sub` credits `mat_sub`, and `ganita_mat_submatrix` credits both.

Reproduced directly: appending **one comment line** to `tests/ganita.tcyr`,
naming `ganita_mat_print(` and calling nothing, moved the reported figure from
**109/135 (80 %) to 111/135 (82 %)**. `mat_print` is called nowhere in the repo.

`state.md` published that table as the project's coverage, and `ci.yml` gated on
`--min 80` against a reported 80 — **zero margin, held up by the artifact**. The
honest word-boundary count at 1.2.2 was **72/135 (53 %)**, and `_compat.cyr` was
**4/53**, not 40/53. Anyone planning the `_compat` removal against "75 %
exercised" was planning against nothing.

**What 1.2.3 does about it**: `state.md` now publishes the honest count and
labels the tool's figure as what it is. The gate is **not** lowered to make a red
build green and **not** left at a number only the artifact satisfies — see
`state.md` for where it now sits and why. The 62 new assertions close the
highest-risk real gaps first, in the order the verifier ranked them:
`mat_dot` (raw pointer arithmetic, zero tests, wrong doc), then
`mat_add`/`mat_sub`/`mat_scale` (which had **zero** assertions and the
out-of-bounds read above), then the `math_advanced` functions.

Still open: the 49 untested `_compat` aliases (all 53 re-verified by hand to
forward verbatim with matching arity and order), and seven genuinely dark
`math_advanced` functions.

## Checked and found clean

Worth recording so the next sweep does not re-litigate them:

- **The 1.0.4 CWE-190 guard in `ganita_mat_new` is correct** — the division form
  cannot itself overflow, and non-positive dimensions are rejected. It is the
  *callers* that were the problem, not the guard.
- **All 53 `_compat` aliases forward verbatim**, with matching arity and argument
  order. None drops or reorders an argument.
- **The 1.2.2 `least_squares` rewrite is sound.** No Q is formed; the reflectors
  reach `b` directly. The wide-matrix defect found here is a missing
  precondition, not a flaw in that design.
- **`_f32_key`'s sign-magnitude transform is correct**, and the native f32
  arithmetic tier really is native — `ganita_f32_add(2^24, 1) = 2^24`, which the
  widened form gets wrong.
- **No command-injection or path-traversal surface exists.** ganita opens no
  files, binds no sockets, spawns no processes, parses no argv, and issues no
  syscall but `write(2)` from `mat_print`. Checklist items 5 and 6 are N/A and
  will stay N/A.

## Sweep metadata

Seven lenses — memory safety, linalg core, linalg advanced, f64 math, f32 math,
performance, contracts/coverage — each followed by an adversarial verifier
instructed to default to *refuted* and to reproduce or refute independently
rather than trust the finder. 14 agents, 480 tool calls, ~2.0 M tokens, 42
minutes wall clock. Verifiers were also asked what the finder **missed**; three
of the findings fixed above came from that second pass rather than the first.

Zero findings were refuted outright, which is a weaker signal than it looks:
the verifiers downgraded six and upgraded three, and the requirement that every
finding carry a *run* repro did most of the filtering before a verdict was ever
reached.
